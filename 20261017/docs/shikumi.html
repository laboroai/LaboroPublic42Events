S3 仕組みの説明

今日作るエージェントの中で、何が起きているか

今日作るのは、質問を受けて、自分で書いたQAを調べ、それをもとに答えるエージェントです。中では3つの仕組みが、この順につながって動いています。どれも、後半のS6〜S8で起きることにつながります。

  1. LLM：次の言葉を確率で選ぶ
  2. ツール呼び出し（Function calling）：LLMが「この関数を呼ぶ」と決める
  3. RAG：検索をツールにして、必要なときに資料を取りに行く

1LLM：次の言葉を確率で選ぶ

LLMは、それまでの文章を読んで、次に来そうな言葉を候補ごとの確率で出します。その確率に従って1つ選び、また次の言葉を選ぶ。これをくり返して文章を作ります。

いちばん確率の高い言葉が毎回選ばれるとは限りません。そのため、同じ質問をしても、聞くたびに文面が変わります。

ためしてみる（数字は説明用のたとえです）

「42 Tokyoの魅力は、」の次に来る言葉の候補:

42 Tokyoの魅力は、…

S8で見ること　同じ質問をもう一度聞くと、前と同じ回答は返ってきません。言い回しが少し変わるだけでも、assert answer == "..." のようなテストは通りません。
Laboroの現場から

仕事でLLMを使うときは、出力が毎回揺れる前提で作ります。揺れをゼロにする設定を探すより、揺れても困らない確かめ方（何を見ればOKとするか）を先に決めておくほうが、結果的に早く進みます。

次へ　LLMは、学習した知識の中から言葉を選びます。今日の合言葉や、皆さんが書くQAのように、学習していないことは知りません。そこで、LLMに「外の情報を取りに行く手段」を渡します。それがツール呼び出しです。

2ツール呼び出し（Function calling）：LLMが「この関数を呼ぶ」と決める

エージェントには、Pythonの関数を「ツール」として渡せます。ただし、LLMが関数を実行するわけではありません。LLMがするのは、「この質問にはこの関数が要る」と決めて、関数に渡す引数を作るところまでです。関数を実行するのはプログラム（今日はADK）で、LLMはその結果を読んでから答えます。

LLMは関数の中身のコードを読みません。読むのは、関数の名前、引数とその型、docstring（説明文）だけです。それを読んで、この質問に答えるのにツールを呼ぶべきかを決めます。

たとえば、こんな関数を渡すと

def get_menu(day: str) -> dict:
    """指定した曜日の学食のメニューを返す。学食や昼ごはんについて聞かれたときに使う。

    Args:
        day: 曜日。「月」「火」のように1文字で渡す。
    """
    ...

LLMに見えているのは、これだけです

名前:   get_menu
説明:   指定した曜日の学食のメニューを返す。学食や昼ごはんについて聞かれたときに使う。
引数:   day（文字列）  曜日。「月」「火」のように1文字で渡す。

「火曜の学食は？」と聞かれると、LLMは get_menu(day="火") を呼ぶと決めます。「こんにちは」には呼びません。

説明文の書き方しだいで、ツールは呼ばれたり呼ばれなかったりします。「何をするツールか」と「いつ使うか」を書いておくと、LLMが判断しやすくなります。
S6で使うコマンド　python try_tool.py で、つないだツールがLLMにどう見えているかを確かめられます。python try_tool.py ツール名 引数 とすると、LLMを通さずに関数だけを呼んで、戻り値を見られます。うまく動かないときは、関数とLLMのどちらに原因があるかを、ここで切り分けてください。
Laboroの現場から

ツールの名前と説明文は、LLMが読む仕様書です。ツールが呼ばれないときは、まずプロンプトより先に説明文を疑います。人が読んでも「いつ使うか」が分からない説明は、LLMにも伝わりません。

次へ　では、LLMに渡すツールが「QAを検索する関数」だったらどうなるでしょう。LLMは、知らないことを聞かれたときに自分で検索を呼び、見つかったQAをもとに答えるようになります。これが今日作るエージェントで、RAGと呼ばれる考え方の一つです。

3RAG：検索をツールにして、必要なときに資料を取りに行く

RAG（検索拡張生成）は、資料を検索して、見つかった内容をもとにLLMに答えさせる考え方です。よく知られた形は、質問が来たら必ず先に検索し、その結果を質問といっしょにLLMへ渡すものです。

今日のエージェントは少し違います。検索はツールの一つで、検索するかどうか、何という言葉で検索するかを、LLMが自分で決めます。「こんにちは」には検索せずに答え、合言葉を聞かれたら検索します。必要なときに、エージェントが自分で資料を取りに行く形です。

検索の中身：意味の近さで探す

検索ツールの中では、言葉が一致するかではなく、意味が近いかで探しています。そのために、文章を数の並び（ベクトル）に変えます。今日使う埋め込みモデル（text-embedding-3-small）では、1つの文章が1536個の数になります。意味の近い文章はベクトルの向きが近くなり、その近さを点数にしたのが、S5の検索コマンドに出る点数です。1に近いほど、意味が近いことを表します。

ためしてみる（2次元に縮めたたとえです。本物は1536次元）

質問を選ぶと、QAとの近さの点数が出ます。言葉が一致していなくても、意味が近ければ点数は高くなります。

順位点数QAの質問

S5で実際に出る画面

$ python search.py "今日のハンズオンの合言葉は？"
「今日のハンズオンの合言葉は？」に近いQA（点数は1に近いほど近い）
  1. 0.829  secret_qa.csv     今日のハンズオンの合言葉は？
  ...

点数は10/9に本物の埋め込みモデルで試したときの値です。このとき2位は0.115で、1位と大きく離れていました。皆さんのQAによって変わります。

LLMは、見つかったQAだけで答えるとは限りません。もともと知っていることも混ぜて答えます。QAに書いていないことが、もっともらしく回答に入ることがあります。
S5〜S7で見ること　S5では、どのQAが何点で返るか、言い回しを変えても引けるかを試します。S6では、この検索をツールにしてエージェントにつなぎます。S7で回答を判定するときは、その一文がQAから来たのか、LLMが足したのかを見てください。判定が割れる理由の一つになります。
Laboroの現場から

回答がおかしいとき、原因はLLMより検索の側にあることがよくあります。直す前に、まず「何が引けていたか」を見ます。今日の ask.py が、呼ばれたツールと引けたQAの点数を毎回表示するのはそのためです。
